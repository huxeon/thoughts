# Pi Harness

Pi Harness 是一个运行在终端里的 Agent 工具。我大概是在四月份从 DeepSeek 官方的工具列表里发现它的，当时爆火的 OpenClaw，底层用的就是它。起初最吸引我的是它的终端界面——我得承认我是个"颜值党"，第一眼的 UI 就让我愿意试下去。

在那之前，主流的 Agent 工具我基本都摸过一遍。DeepSeek-TUI（现在改名叫 CodeWhale）是我最初挺喜欢的一个，后来觉得质量一般就放弃了；Reasonix 用了挺长时间，它最出名的是高缓存设计，可惜前后重构了好几次，后面的设计我不太喜欢；Claude Code 因为一些让人难受的操作被我弃了；OpenCode 我到现在还在用，但总觉得它功能太多，缓存设计也不太友好。Pi 是唯一一个让我真正留下来的——留住我的有三个点：默认无权限、`!/!!` 输入命令、还有 `/tree`。

先说说默认无权限。说实话，一开始我觉得这是一件很恐怖的事，尤其那时候网上到处都在说 Agent 把系统搞乱了。但真正用起来，我发现自己对不断弹出的权限提示非常烦，而且几乎每次都点了允许——这么一想，默认无权限反而才是对的。后来我听到了 Pi 创始人的想法：Agent 实际上就是你自己，在默认无权限的情况下，你会更加慎重地考虑，逼着你自己思考。我挺认同这个观点。而且后来的模型训练也在不断加强这部分，从我开始用到现在，它从来没搞乱过我的系统，反而帮我处理了不少系统相关的问题；换作别的 Agent，我大概会不停地点 Allow 吧。更何况 Pi 的定位是一个 Agent 底座，默认无权限更符合这种定位——如果默认就放权，下游想改权限管理方式的时候，不就炸了吗。

`!/!!` 对我来说非常自然。我是个忠实的终端用户，之前用得最多的编辑器是 Helix，它本身就有调用 bash 命令的能力，所以这个设计一下就戳中了我，这也是 Pi 第二吸引我的地方。我认为它极大地扩展了 Pi 的边界：以前想在 Agent 里执行点别的操作，多半要另开一个终端或者用 tmux，现在直接在输入框里就能调用小命令，从这个角度看，它相当于内置了一个操作系统的控制台（当然只是一部分，需要完整终端的命令还是得写扩展）。现在我的一个工作流就是在输入框里 `!!code .` 打开 VS Code；之前还写过一个 `pi-hx` 扩展，用来在 Pi 里开 Helix，但现在用得少了。

`/tree` 是第三个吸引我的地方。它有一种 Git 分支的感觉，给了很大的自由度。Agent 圈子里那些功能——subagent、btw，还有 handoff 之类的 skill——其实都能用 tree 来实现。我把 subagent 分成两类：探索性的和执行性的。前者需要把子代理的结果详细回传，用 `tree + compact` 就能把结果送回原来的位置；后者只要执行结果，直接 `!!pi -p xxx` 或者 `!!tmux xxx` 就行，相当灵活。btw 虽然可能提供不了异步方式（也许 Pi 的新架构可以），但同步执行再回到原位置是没问题的；handoff 同样是 `tree + compact`，Pi 还支持自己选压缩方式，实现起来轻轻松松。

如果站在我的角度总结，Pi 的设计哲学是"把控制权交还给人"。官网那句标语是"提供一个极简的核心，在此基础上按照需求自行扩展"，我也认同；但作为用户，我最关心的其实是和产品的交互方式。Pi 不只是给 LLM 提供的一套运行时，更是一座让人和 LLM 共同工作的桥梁。

顺着"自行扩展"，我也真的动手写过扩展。老实说，我对 Pi 提供了哪些扩展接口只有少量了解，所以 `pi-hx` 和 `pi-qq` 都是 vibe coding 的产物——把想法告诉 LLM，它自己实现。`pi-hx` 的灵感来自 Pi 里按 Ctrl+G 打开外部编辑器的机制，我想着同样可以做一个通用的 `/hx` 命令；用得不多，是因为功能有些简陋、还有些 bug，加上我对 TypeScript 本来就不太熟，后来发现用终端复用器或者 `!!code` 已经能满足需求了。`pi-qq` 是我读完 QQ 机器人的文档之后让 Pi 帮我实现的，基础功能有了，但也因为简陋、提供不了 Pi TUI 的全部能力而用得不多。这两个扩展虽然粗糙，却实实在在地证明了 Pi 的扩展能力。

真正让我挠头的是 web search。我写过一个基于 DeepSeek Responses API 的 web search 扩展，写了好几版，都停在"能用但不好用"。最初我是想直接在 Pi 里用基于 Responses API 的 DeepSeek，可惜 Pi 并不支持完整的 Responses API——虽然能在发请求前改写请求体，但官方文档要求回传响应，我试了几次都没找到直接的口子，除非重写整个 `streamSimple`。维护成本太高，不值当，最后我干脆用了社区的 Web Search 插件。这里我其实不太确定该不该怪 Pi：也许它留的扩展接口确实还不够，但更可能是我自己能力有限。我倒是希望 Pi 能支持自定义改写当前的 messages 数组（也就是存放上下文的地方）——也许它早就提供了，只是我和 LLM 都没找到。

说到 vibe coding，这更多是自嘲。现在我的原则是：简单或者明确的任务，交给 Agent 全权负责。简单，指我自己也能写出来、纯属体力活的那种；明确，指已经和 AI 详细讨论过、留下了完整规格说明的那种。我经常用 mattpocock 的 grill-me skill（以及它的变种 grill-with-doc），经过详细讨论后会产出一个 spec 和若干 tickets，然后让 Agent 去实现，我退到监管的位置，跑偏了就拉一把。面对一个完全陌生的领域，我会先自己或让 Agent 找材料，宏观了解个大概之后才启动 Agent 流程，并把我已知的东西告诉它。最重要的是：Agent 给出的代码，我要能看懂、能审查。虽然 TypeScript 我不太熟，但编程语言的知识储备还在——Rust、C/C++、Java、Python、Lisp——很多概念是互通的。这条线，大概就是"控制权还给人"在我身上的具体样子：不是每件事都亲自动手，而是始终保持能接手、能兜底的能力。

回到"底座"这个词。底座意味着实现了 Agent 的核心部分，之后无论其他 Agent 添加什么功能，都能在它上面用扩展的方式实现。目前 Pi 选的是 Agent-Loop、Tools、Skills + Extension 这条路线，短期内我觉得没什么问题，MCP、多智能体这些目前也都能实现。最近我也看到了新的范式——DeepSeek Harness，它可能更接近"底座"的字面意思，连 Agent-Loop 都是可替换的。但我并不完全推崇"底"这件事：越是底层，离易用性就越远。这一点上我认为 Pi 做得比 DeepSeek Harness 好——我日常就是裸 Pi 加一些 skills 和一个 web search 扩展，运行良好，可以打 8 分左右。

扣分主要在扩展的质量。社区里有些用的人很多的扩展，代码质量并不行，也不符合 Pi 的极简哲学。我更希望官方能维护一套常用扩展，或者有一个仓库来说明哪些扩展在功能、易用性、代码质量上达到了不错的水平。目前 Pi 仓库确实有一套扩展示例（packages/coding-agent/examples/extensions），功能上还可以，但安装不够便捷。

再往后看一两年，我说不太清楚——去年 AI 的热点是 CoT，今年是 Agent，明年后年是啥真的难以预料。Pi 其实不必去学 DeepSeek Harness，现在的可扩展性加上易用性已经达到了还不错的水平。我对它的期待主要有两个：一是把扩展生态抓起来，维护一些质量高的常用扩展；二是它最近在重构，可能会叫 Pi 2，我在新仓库里看到了 client、protocol、server，我还是挺期待这套 CS 架构的——一套后端、若干前端，TUI、Web、Desktop 都会因此变得更好。我一直希望能在手机或电脑上使用远程的 Pi，目前生态里的方案还远不够成熟。

如果非要用一句话概括 Pi Harness 对我的意义，那就是：它让你在 LLM 和 Agent 中找到自己的位置。我依然希望在 AI 的发展中一直有人的位置，而 Pi 让我觉得，这个位置是可以由我自己来定义的。
