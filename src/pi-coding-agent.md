# Pi Coding Agent

在 Agent 工具之间换了一圈之后我才意识到：选工具，其实是在选一种和 AI 相处的方式。这篇就聊聊最终留下来的那个——Pi Coding Agent。

## 从换工具说起

在遇到它之前，我在终端 Agent 里已经辗转过一轮。DeepSeek-TUI（如今改名 CodeWhale）是一位国外开发者做的，最初挺喜欢，后来发现质量一般，放弃了；Reasonix 以高缓存设计出名，几番重构之后的设计不合我的口味，也放弃了；Claude Code 则是败在这家公司各种离谱的操作，外加那份日益增长的无用功能列表；用得最久的是 OpenCode，但总觉得功能太多，缓存设计也不太友好。

四月份，我在 DeepSeek 官方的工具列表里看到了 Pi Coding Agent——当时爆火的 OpenClaw，底层也是它。最先吸引我的是它的终端界面，我确实是个颜值党。但真正让我留下来的，是另外三样东西。

## 三个留下来的理由

**默认无权限。** 我曾经觉得这是一件很恐怖的事，当时到处都是 Agent 搞乱系统的传闻。但用着用着我发现，自己对不断弹出的权限提示越来越烦，而且几乎每一次都点了允许——既然如此，或许默认无权限才是对的？后来听到 Pi 创始人的说法：在没有权限提示兜底的情况下，你会更慎重地考虑每一条指令，这反而逼迫你自己思考。我认同这个观点，后续的模型训练也在逐渐加强这方面。从使用到现在，Pi 没搞乱过我的系统，反倒帮我处理了不少系统问题——换成别的工具，我大概会在权限弹窗里点 Allow 点到手软。何况 Pi 定位为 Agent 底座，默认无权限也更合理：如果默认就带上一套权限管理，下游想换掉它的时候，岂不是就炸了。

**`!/!!` 输入命令。** 对忠实的终端用户来说，这再自然不过——我此前的主力编辑器 Helix 本来就有调用命令的功能，但在 Agent 工具里，这是我头一次见到。它极大地扩展了 Pi 的边界：以前想在 Agent 会话里执行点别的操作，多半得再开一个终端或者挂个 tmux；现在随手一个 `!` 就行（`!command` 会把输出发给模型，`!!command` 则只执行、不打扰模型）。某种意义上，它相当于内置了半个操作系统控制台。我现在的固定工作流，就是在输入框里敲 `!!code .` 打开 VSCode。

**`/tree`。** 这是三个里最惊艳我的，有种 Git 分支的感觉，提供了很大的自由。当时各家工具已经有了 subagent、btw、handoff 这些功能，而在 Pi 里，它们多半可以用 tree 组合出来。子代理我分两种：探索性的那种需要详细回传结果，用 tree 开出去，compact 之后把结论带回原来的位置；执行性的那种只要个结果，直接 `!pi -p xxx` 或者 `!tmux xxx` 更省事。btw 可以同步执行再跳回来（异步或许要等新架构）；handoff 同样是 tree+compact，还能自选压缩方式。极简的核心，组合起来反而无所不包。

在我看来，这就是 Pi 的设计哲学——**把控制权交还给人**。官网的标语是"提供一个极简的核心，在这个基础上按照需求自行扩展"，我认同这句话；但作为用户，体感最深的还是交互方式：它不只是给 LLM 准备的一套运行时，更是人和 LLM 共同工作的桥梁。

## 亲手撞一次墙

说 Pi 可扩展，不是句空话，是可以动手验证的。我对 Pi 的扩展接口其实只有少量了解，所以 pi-hx（借用 Ctrl+G 外部编辑器的机制，做一个 `/hx` 命令在 Pi 里打开 Helix）和 pi-qq（照着 QQ 机器人文档实现的客户端）都是 vibe coding 的产物——把想法告诉 LLM，它自行实现。两个扩展都停在"能用但简陋"的阶段，现在用得也不多，但它们确实证明了这条路走得通。

真正让我撞墙的是 Web Search。我最初想直接在 Pi 里用基于 Responses API 的 DeepSeek，但 Pi 不支持完整的 Responses API。改写请求体倒是可以做到，可官方文档要求把响应回传，我试了几次也没找到直接的接口，除非重写整个 streamSimple——维护成本太高，不值得。最后我用了社区的插件。当时我许愿 Pi 能开放自定义修改 messages 数组（存放上下文的地方）的能力，后来才发现这个接口其实是有的：`context` 事件会在每次 LLM 调用前触发，`event.messages` 是可以安全修改的深拷贝，返回替换后的数组即可。至于响应侧，`after_provider_response` 只能读到 status 和 headers，"回传响应"的问题依旧。所以说到底不是接口不够，而是文档的发现性不好——我和 LLM 都没能找到它。

## 我和 Agent 的分工线

前文说 vibe coding，更多是自我调侃。现在，简单或者明确的任务，我会让 Agent 全权负责。简单，是指我自己也写得出来、纯属体力活的那种；明确，是指我和 AI 已经详细讨论过、留下了完整 spec 的那种。我常用 mattpocock 的 grill-me skill（以及它的变种 grill-with-doc），几轮拷问之后会产出一个 spec 和若干 tickets，接下来 Agent 负责实现，我负责监管，跑偏了就拉一把。碰到完全陌生的领域，我会先自己或让 Agent 找些材料，对全局有个概念之后再开 Agent 流程，并把我知道的都告诉它。最重要的是，Agent 给出的代码，我必须能看懂、能审查——TypeScript 我不算熟，但 Rust、C/C++、Java、Python、Lisp 的底子还在，很多概念是互通的。

所谓"把控制权交还给人"，不是凡事亲力亲为，而是人始终保有能接手、能兜底的能力。

## 底座这回事

底座，意味着实现的是 Agent 的核心部分：后续无论别家 Harness 加什么功能，都应该能在这个基础上扩展出来。写这篇时我专门去翻了文档核对，Pi 的核心比我记的还要小：Agent-Loop 加一套内置工具，仅此而已；Skills、Extension、提示词模板、主题、pi packages，都是官方留出的扩展通道。README 的 Philosophy 一节甚至把"没有什么"列成了清单：No MCP、No sub-agents、No permission popups、No plan mode、No built-in to-dos、No background bash，每一条后面都缀着一句"可以用扩展自己搭"。所以 MCP、多智能体并非不能有，只是不内置。最近出现的新范式 DeepSeek Harness 或许更接近"底座"的字面意思——连 Agent-Loop 都是可替换的。但我并不完全推崇"底"：越是底层，离易用性就越远，这方面 Pi 做得比 DeepSeek Harness 好。我的日常就是裸 Pi 加几个 Skills 和一个 Web Search 扩展，运行良好。

要给 Pi 生态打个分的话，8 分左右。扣分主要在扩展质量：社区里一些用得很多的扩展，代码质量并不行，也不符合 Pi 的极简哲学。我更希望官方维护一套常用扩展，或者有一个仓库，标注哪些扩展在功能、易用性、代码质量上达到了水准。Pi 仓库确实有一套扩展示例（packages/coding-agent/examples/extensions），功能尚可，安装不够便捷。

## 期待

我对 Pi 的期待有两个。一是把扩展生态抓起来，维护一些高质量的常用扩展；二是正在进行的重构——可能会叫 Pi 2，新仓库里已经能看到 client、protocol、server。我很期待这套 CS 架构：一套后端、若干前端，TUI、Web、Desktop 都会因此受益。我一直想在手机和电脑上用上远程的 Pi，目前生态里的方案还远不够成熟。

再往后一两年会怎样，我说不好。去年大家聊 CoT，今年聊 Agent，明年聊什么，很难预料。我只希望，在 AI 的发展中一直有人的位置。

Pi Harness 让你在 LLM 和 Agent 中找到自己的位置。
